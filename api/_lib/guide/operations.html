Operations (moderators only)

This section is for the moderators and whoever maintains the site. It describes how the site is hosted and how to keep it running. It deliberately contains no passwords, keys or key file contents; those live only on the server and with the masjid’s account owners. The repository is public, so never paste a secret into the repo, an issue, a chat or an email.

The authoritative technical notes live in the repository: docs/self-hosting.md, deploy/backup/README.md and deploy/migrate/README.md. If this page and those files ever disagree, trust the files.

Architecture

Everything runs on one AWS Lightsail server owned by the masjid (address 3.21.108.22, domain noorbusiness.org).

Request flow: the browser talks to Nginx. Paths starting /api/, /b/<id> and /sitemap.xml go to the API on port 3001. Paths /rest/v1, /auth/v1, /storage/v1 and /realtime/v1 go to Supabase on port 8000. Everything else is a static file.

Where secrets live: only in /etc/noorbusiness/api.env, /etc/noorbusiness/backup.env and /opt/supabase/docker/.env. Templates with empty values are in the repo as deploy/api.env.example and deploy/backup/backup.env.example. Do not copy the real files anywhere insecure.

Server access

You sign in to the server over SSH with a key. The SSH key is held by the masjid’s AWS administrator. Never share it by email, chat or the repo. A new maintainer should be given their own access by that administrator (for example by adding their public key), and removed the same way when they leave.

  • Connect: ssh ec2-user@3.21.108.22 (using your key). Use sudo for the commands below.
  • Open Supabase Studio from your own computer with a tunnel: ssh -L 3000:127.0.0.1:3000 ec2-user@3.21.108.22, then visit http://localhost:3000 in your browser. Close the tunnel when you are done.
  • The Lightsail console (AWS, masjid account) can open a browser terminal and show the server’s status, snapshots and firewall.

Deploying an update

  1. Make the change on a branch in GitHub and get it reviewed. The tests run automatically on every push.
  2. Merge to main.
  3. On the server run: sudo bash /opt/noorbusiness/deploy/deploy.sh

The script pulls main, copies the public files to /var/www/noorbusiness, installs the Nginx config, runs the tests, restarts noorbusiness-api and checks it. It never touches DNS, certificates, Supabase or secrets. To try a branch first: sudo bash /opt/noorbusiness/deploy/deploy.sh my-branch, and deploy main again afterwards. If the script stops on a failing test, do not work around it; read the message and fix the cause.

Database changes are SQL files in supabase/migrations/. They are applied once, in date order, from Studio’s SQL editor (or psql in the database container), and are safe to re-run. The README lists the order.

Backups

  • Nightly at 3:15 AM (America/New_York) a backup is written to /var/backups/noorbusiness: the database, the roles, the photo storage and the configuration (which contains secrets, so keep the folder private).
  • The server keeps 14 daily and 8 weekly copies.
  • Once BACKUP_S3_URI is configured in backup.env, each night is also copied to the masjid’s private S3 bucket, so a copy survives if the server is lost. If it is empty, nothing leaves the server. Confirm it is set.
  • A weekly restore test (Sundays) restores the latest dump into a throwaway container and checks that listings and users are there. A failure emails the alert address.
  • Useful commands: systemctl list-timers 'noorbusiness-*', journalctl -u noorbusiness-backup -n 50, sudo systemctl start noorbusiness-backup (take a fresh backup before any risky change).

Restoring

Follow deploy/backup/README.md, section “Restoring for real”. In short: fetch the chosen day from S3 (or use the local copy), check it with sha256sum --check SHA256SUMS, restore the configuration first on a fresh server so the keys match the users, then restore the database and photos. Take a fresh backup before restoring over a running server, and practise on a spare machine before you need it.

Health alerts

Every 5 minutes noorbusiness-healthcheck checks disk, memory, the nginx, noorbusiness-api and docker services, the site and /healthz, the Supabase containers, the HTTPS certificate expiry and the age of the newest backup. Problems are emailed through Amazon SES to ALERT_EMAIL_TO; the same problem is emailed at most once every 6 hours, and one “RECOVERED” email follows when all is well. A dead server cannot email, so also keep the Lightsail StatusCheckFailed and CPU alarms set to notify a different mailbox.

HTTPS

Certificates are free ones from Let’s Encrypt, issued by certbot through Nginx, and they renew automatically. The health check warns 14 days before expiry. To test renewal: sudo certbot renew --dry-run. If a renewal fails, read journalctl -u certbot-renew (or /var/log/letsencrypt/letsencrypt.log); the usual cause is DNS no longer pointing at this server.

DNS

DNS is in Route 53 in the masjid’s AWS account. The records that matter are A records for noorbusiness.org and www.noorbusiness.org, both pointing to 3.21.108.22. Never edit or delete MX records; they make email work. If the server is ever rebuilt with a new address, update both A records, then re-run certbot. Keep the Lightsail static IP attached so the address does not change by accident.

Adding the first moderator

The very first moderator cannot be added from the site because there is nobody to add them. Have the person create an account and turn on two-factor, then run the SQL under “The very first moderator” in README.md in Studio’s SQL editor, with their email. After that, moderators manage the Team tab themselves.

Rotating secrets

Rotate a secret when a person with access leaves, when it may have been exposed, or on a regular schedule.

  1. Create the new value at its source (the AWS IAM console for the SES keys, Cloudflare dashboard, a fresh random string for NOTIFY_SECRET and IP_HASH_SALT).
  2. Edit the matching line in /etc/noorbusiness/api.env (or backup.env) with sudo.
  3. Restart: sudo systemctl restart noorbusiness-api.
  4. Revoke the old value at its source, then send a test (a contact-form message) to confirm email still works.

The Supabase JWT secret and its anon and service keys are different: changing them signs everyone out, breaks the site until the new anon key is applied (deploy.sh copies it from api.env into the site), and affects the database trigger that calls the API. Do this only with a fresh backup, a quiet hour and the instructions in the Supabase self-hosting documentation. If NOTIFY_SECRET changes, the alert trigger SQL in the database must be updated with the same value.

To remove a leaver’s server access, ask the AWS administrator to remove their key. Also remove them from the Team tab and from GitHub.

Troubleshooting checklist

Always start with the basics: what changed recently, and what do the logs say?

The site is down or shows an error
  1. Can you reach the server? ssh in. If not, check the Lightsail console and restart the instance from there.
  2. sudo systemctl status nginx noorbusiness-api docker supabase
  3. curl -s http://127.0.0.1:3001/healthz should answer {"ok":true}.
  4. sudo nginx -t, then sudo systemctl reload nginx; logs in /var/log/nginx/error.log.
  5. sudo journalctl -u noorbusiness-api -n 100 --no-pager
Listings do not load, or sign-in is broken
  1. cd /opt/supabase/docker && sudo docker compose ps. Everything should be running and healthy.
  2. Look at the unhealthy one: sudo docker compose logs --tail 100 <service> (for example db, auth, kong, rest).
  3. Restart it: sudo docker compose restart <service>, or all of it: sudo systemctl restart supabase.
  4. If only sign-in or sign-up fails, check Cloudflare Turnstile is reachable and its keys in api.env still match, and that the site address in api.env is correct.
  5. If the site loads but cannot reach data after a deploy, check SUPABASE_ANON_KEY is set in api.env (the deploy script prints a warning if not).
Emails are not sending
  1. Check the Amazon SES console (in the region set by AWS_SES_REGION): is the noorbusiness.org identity still verified, is the account still out of the sandbox, and is it within its sending limits or under review?
  2. Check AWS_SES_ACCESS_KEY_ID, AWS_SES_SECRET_ACCESS_KEY, NOTIFY_EMAIL_TO and NOTIFY_EMAIL_FROM in api.env are set (never print the key into a chat or ticket).
  3. Read sudo journalctl -u noorbusiness-api -n 100 --no-pager for send errors.
  4. Alerts come from database triggers. If the secret in the trigger SQL no longer matches NOTIFY_SECRET, the API rejects them. Do not also create Supabase “Database Webhooks” for the same tables, or alerts arrive twice.
Disk is full (or the 85% alert)
  1. df -h, then sudo du -xh /var/backups /var/lib/docker /var/log --max-depth=1 | sort -h | tail
  2. Backups: sudo du -sh /var/backups/noorbusiness. Do not delete the newest ones.
  3. Free Docker space: sudo docker system df, then sudo docker image prune (only unused images). Trim old logs with sudo journalctl --vacuum-time=14d.
  4. If it keeps filling, enlarge the Lightsail disk or move to a bigger plan.
A container is unhealthy or keeps restarting
Run sudo docker compose ps and sudo docker compose logs --tail 100 <service> in /opt/supabase/docker. Low memory is a frequent cause: check free -m and the health alert for memory and swap. Restart with sudo docker compose restart <service>. If the database container itself will not start, stop and take advice before changing anything; do not delete volumes.
Certificate warning in the browser
See HTTPS above: sudo certbot renew --dry-run, then sudo certbot renew if it is due.
A backup alert
sudo journalctl -u noorbusiness-backup -n 100 --no-pager. Usual causes are a full disk or the S3 keys being revoked. Run sudo systemctl start noorbusiness-backup after fixing it.
The Moderation page says you are not allowed
Check you are on the Team tab with the right email and signed in with two-factor. If nobody can get in, a maintainer with server access can add a moderator with the SQL from the README.

When in doubt, take a fresh backup first (sudo systemctl start noorbusiness-backup), write down what you change, and change one thing at a time.

Handing over to a new maintainer

  1. Have the masjid’s AWS administrator give them their own server access (never pass on someone else’s key) and remove the previous maintainer’s.
  2. Walk through this page and the three technical documents in the repository together, and have them perform a deploy and read a backup log.
  3. Confirm the masjid owns each outside account (AWS, Cloudflare, GitHub) and that at least two trusted people can sign in to each.
  4. Check that the off-server backup is configured, that the last weekly restore test passed, and that a copy of the server’s secret files is stored somewhere safe and separate (for example the masjid’s password manager), never in the repo.
  5. Make sure there are at least two moderators, and that health and backup alerts go to a mailbox more than one person reads.
  6. Rotate any secret the previous maintainer knew.
  7. Record the date and the names in the Activity notes or the masjid’s own records.

Making changes with Claude

Claude Code is an AI assistant that can read and change the site’s code. A maintainer who is not a full-time developer can use it to fix bugs, change wording or add small features. Use it on the web at claude.ai/code or in the Claude desktop app. Claude works on a branch, a separate copy of the code. Nothing changes on the live site until a person merges the work and deploys it.

The safe routine

  1. Open Claude Code, connect GitHub and choose the repository (Chippy412/noorbusiness, or its new masjid-owned home).
  2. Describe the change in plain words: what you see now, and what you want instead.
  3. Make sure Claude works on a new branch and never changes main directly.
  4. Ask Claude to run the tests and show you the result: node --test tests/*.test.js.
  5. Ask Claude to open a pull request and explain it in plain words. Read the summary and the list of changed files. If something looks wrong or bigger than expected, ask questions before going further.
  6. When you are satisfied and the automatic tests pass on GitHub, merge the pull request into main.
  7. Deploy on the server: sudo bash /opt/noorbusiness/deploy/deploy.sh (see “Deploying an update”).
  8. Open the live site and try the thing you changed. If something broke, ask Claude to revert the change, then merge and deploy again.

If a change needs a database update (a new file in supabase/migrations/), Claude should say so. Take a fresh backup first, then apply the file from Studio’s SQL editor. The deploy script does not run migrations.

Keep secrets out of the chat

  • Never paste passwords, API keys, tokens or the SSH key file into Claude or any other chat.
  • Secrets belong only in the server’s env files (see “Where secrets live”). If Claude needs to know a setting exists, give it the name only, for example AWS_SES_SECRET_ACCESS_KEY.
  • If a secret is pasted by mistake, rotate it right away (see “Rotating secrets”).
  • Do not let Claude change the live server, DNS or the database directly unless a trusted maintainer is watching and has said yes to each step.

The repository is public

This Guide is only shown to the signed-in team, but the GitHub repository can be read by anyone. Keep private details (people’s phone numbers, internal contacts, anything sensitive) out of the repository, including this Guide’s files in api/_lib/guide/. Keep them in the masjid’s own records instead.

Updating this Guide

This Guide lives in api/_lib/guide/team.html (everyone on the team) and api/_lib/guide/operations.html (moderators). When something changes, such as a new server, a new account or a new moderation rule, ask Claude to update the right file, then review, merge and deploy as above.

Example requests

  • “On the moderation page, add a filter in All listings for listings with no photo. Work on a new branch, run the tests and open a pull request.”
  • “The Contact page shows the wrong phone number. Find it and fix it. Show me the change before you commit.”
  • “Add a new badge called Student friendly. List every file you need to change, including the database, before changing anything.”
  • “A moderator says new-listing emails are not arriving. Read the code that sends them and tell me the likely causes. Do not change anything yet.”
  • “Update the Guide’s DNS section: the masjid moved DNS to a new provider. Do not add any secrets.”
  • “Explain this pull request in plain English, and tell me what could go wrong when we deploy it.”

Good habits

  • Ask for one small change at a time.
  • Ask Claude to explain its plan before it changes anything big.
  • Never deploy a branch you have not looked at. The normal deploy uses main.
  • Take a backup before any database change, and avoid deploying right before a busy time.

Retiring the old setup

Before the move, the site ran on Vercel with a hosted Supabase project. They are kept for a short time as a fallback only. Once the new server has run without problems for one to two weeks:

  1. Confirm that noorbusiness.org and www point to the masjid’s server and HTTPS works.
  2. Take a final export of the old hosted database and keep it with the masjid’s records, in case something was missed.
  3. Delete the old Vercel project and pause, then delete, the hosted Supabase project. Its database password and secret key were shared in a chat during the move and have been rotated. Do not reuse them.
  4. Remove the old services’ keys from any password manager, and record the date in the masjid’s records.
